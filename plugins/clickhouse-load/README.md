# Нагрузчик ClickHouse

Плагин `clickhouse` запускает `clickhouse/clickhouse-server:25.8.4.13` и
`dbehave/clickhouse-load:0.1.0`. На каждый запуск worker создаёт отдельные контейнеры,
сеть и том с данными. После завершения они удаляются; история, параметры и метрики
остаются в платформе. HTTP-порт ClickHouse не публикуется на компьютере.

## Запуск

Из корня репозитория:

```sh
docker compose -f infra/compose.yaml up --build --wait
```

Откройте [фронтенд](http://localhost:3000), выберите **ClickHouse 25.8** и сценарий.
Дополнительные настройки Docker или ручная регистрация плагина не нужны.
[Swagger](http://localhost:8080/swagger-ui.html) и
[дашборд ClickHouse](http://localhost:3001/d/dbehave-clickhouse) доступны отдельно.

Если в существующем `.env` уже задан `WORKER_ALLOWED_IMAGE_PREFIXES`, добавьте к
нему `docker.io/clickhouse/`. В новом `.env.example` и настройках Compose этот
префикс уже включён.

По умолчанию база получает 1,5 ядра и 1536 МиБ, нагрузчик — 0,5 ядра и 256 МиБ.
`maxThreads` ограничивает потоки одного запроса, `maxMemoryUsageMB` — память одного
запроса; это не лимиты всего сервера. Лимиты контейнеров задаются отдельно в форме.
Для работы в локальном стенде сервер запускается с ограниченными фоновыми пулами:
пул слияний — 4 потока, общий пул — до 128. Эти значения одинаковы для всех
сценариев; результаты относятся к такой конфигурации, а не к серверным defaults.

## Четыре сценария

### 1. `small-inserts` — мелкие вставки и Buffer

Параллельные клиенты вставляют пачки по `batchSize` строк. Флажок `buffered`
переключает адресат: обычная таблица `MergeTree` или таблица `Buffer`, которая
накапливает строки в памяти и сбрасывает их в ту же `MergeTree` более крупными
блоками. `payloadBytes` задаёт размер полезных данных строки.

У ClickHouse каждый небольшой синхронный INSERT может создавать новую часть
данных. При высокой частоте вставок фоновые слияния не успевают их объединять:
растут число частей, затраты CPU и задержки, возможна ошибка `TOO_MANY_PARTS`.
Buffer показывает, как накопление пачек снижает эту нагрузку. Это отдельный
механизм; настройка `async_insert` в этом сценарии не используется.

Сравните два запуска с `batchSize=1`, `clients=4`, `durationSec=30`, меняя только
`buffered`. Затем увеличьте `batchSize` до 1000 при выключенном Buffer.
Смотрите на подтверждённые строки в секунду, p95 INSERT, число активных частей,
фоновые слияния и ошибки. После нагрузки нагрузчик принудительно сбрасывает Buffer
и проверяет количество строк в целевой таблице.

Подтверждение вставки в Buffer означает приём в память. При аварии сервера ещё не
сброшенные данные теряются. Поэтому меньшую задержку Buffer нельзя трактовать как
ускорение записи с теми же гарантиями сохранности.

### 2. `sorting-key` — отсечение данных ключом сортировки

Генератор создаёт `datasetRows` строк. В каждом запросе он выбирает диапазон
`rangeRows` значений ключа и вычисляет агрегат. С `sortedKey=true` этот ключ стоит
в `ORDER BY` таблицы. С выключенным флажком строки упорядочены по другому,
независимому ключу; условие запроса остаётся прежним.

Разреженный первичный индекс MergeTree позволяет пропускать гранулы, если
предикат согласован с ключом сортировки. При неподходящем `ORDER BY` тот же
логически селективный запрос может прочитать почти всю таблицу. Сценарий показывает,
почему выбор ключа сортировки в ClickHouse часто важнее числа возвращаемых строк.

Сравните `sortedKey=true/false` при одинаковых `datasetRows=300000` и
`rangeRows=1000`. Смотрите на прочитанные строки и байты на запрос, p95 и запросы
в секунду. Размер диапазона ограничен размером набора. Здесь нет отдельного
Bloom-индекса: проверяется именно эффект ключа сортировки.

### 3. `bloom-filter` — поиск по полю вне ключа сортировки

Данные упорядочены по числовому ключу, а запрос ищет точное значение строкового
идентификатора с высокой кардинальностью. Флажок `bloomFilter` добавляет
data-skipping индекс `bloom_filter` по этому строковому полю. Набор и предикат
при этом одинаковы.

Обычный ключ сортировки не помогает такому поиску. Bloom-фильтр может доказать,
что в грануле нет искомого значения, и пропустить её. Фильтр допускает ложные
срабатывания: некоторые лишние гранулы всё равно читаются. Он не заменяет
уникальный индекс и не гарантирует постоянное время поиска.

Сравните `bloomFilter=true/false` на `datasetRows=300000` или большем наборе.
Смотрите на прочитанные строки и байты на запрос, p95, пропускную способность
и размер данных на диске. На маленькой таблице выигрыш по времени может быть
незаметен; уменьшение объёма чтения лучше объясняет работу индекса.

### 4. `replacing-merge-tree` — версии строк и цена FINAL

Генератор записывает `versions` версий каждого из `datasetRows` логических ключей
в `ReplacingMergeTree(version)`. Читающий запрос агрегирует данные с `FINAL`,
если включён `finalRead`, или без него. У каждой следующей версии другое значение,
поэтому разница видна и в количестве строк, и в результате агрегата.

ReplacingMergeTree удаляет старые версии при фоновых слияниях, а не сразу после
INSERT. Без `FINAL` чтение до слияния может учитывать несколько версий одного
объекта. `FINAL` применяет логику замещения во время запроса: результат корректен,
но чтение требует дополнительных ресурсов.

Для воспроизводимости слияния тестовой таблицы при подготовке и замере
приостановлены. Это намеренный способ показать состояние до слияния, а не модель
обычной работы сервера. После проверки слияния включаются обратно.

Сравните `finalRead=true/false` при `datasetRows=100000`, `versions=3`.
Проверьте физическое число строк, число логических ключей и число строк в результате
чтения. С `FINAL` должно быть 100000 строк, без него — 300000 до слияния.
Затем сравните p95, объём чтения и CPU. Это сценарий о согласованности результата
и стоимости дедупликации, а не о транзакционных UPDATE.

## Как сравнивать

Меняйте один флажок за раз, сохраняя набор, длительность, клиентов и ресурсы.
Подготовка набора не входит в основную нагрузку. Прогрев задаётся через `warmupSec`.
Замеры показывают работу на данном Docker-хосте, включая файловый кеш; сценарии
чтения не обещают холодного диска.

Кеш результата запроса и query condition cache отключены, чтобы они не скрывали
разницу в объёме чтения. Журнал `query_log` для запросов нагрузчика тоже отключён:
при частых запросах он сам создаёт заметную нагрузку и расход памяти. Серверные
`read_rows` и `read_bytes` берутся из заголовка `X-ClickHouse-Summary`, без журнала.

Один сценарий запускается отдельными экспериментами. Для ссылки с несколькими
запусками используйте API:

```http
POST /api/experiments/compare
Content-Type: application/json

{"runIds":["UUID-первого-запуска","UUID-второго-запуска"]}
```

API проверяет совпадение сценария и шаблона дашборда. Ссылка сохраняет `kiosk=1`,
выбор запусков, диапазона времени и частоты обновления. Параметры каждого запуска
можно раскрыть на его странице во фронтенде.

## Пример запроса

```sh
curl -X POST http://localhost:8080/api/experiments \
  -H 'Content-Type: application/json' \
  -d '{"pluginId":"clickhouse","scenarioId":"small-inserts","params":{"batchSize":1,"buffered":true}}'
```

Неуказанные параметры заполняются значениями формы. Нагрузчик принимает настройки
и параметры через переменные окружения: `MAX_THREADS`, `MAX_MEMORY_USAGE_MB`,
`SCENARIO`, `CLIENTS`, `DURATION_SEC`, `WARMUP_SEC` и имена полей в
`UPPER_SNAKE_CASE`. Подключение: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
`DB_PASSWORD`. Для worker остаётся общий контракт `GET /health` и `GET /metrics`.

## Проверки

Модульные тесты:

```sh
./gradlew :plugins:clickhouse:test :plugins:clickhouse-load:test
```

Для интеграционных тестов нужен отдельный ClickHouse 25.8 с пользователем
`dbehave`, паролем `dbehave` и правами на создание тестовых баз:

```sh
DBEHAVE_TEST_CLICKHOUSE_URL=http://127.0.0.1:8123 \
  ./gradlew :plugins:clickhouse-load:test
```

Тесты создают и удаляют собственные базы. В CI эти проверки выполняются на живом
ClickHouse, а не на SQL-моках.
