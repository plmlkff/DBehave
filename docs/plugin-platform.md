# Платформа плагинов и контракт воркера

## Каталог

В `dbehave.plugins` лежат `id` и `definition jsonb`. Определение содержит:

- `id`, `title`, `collectorId` — идентификатор, название и id бина `ContextCollector`.
- `loaderImageName`, `databaseImageName` — конкретные имена Docker-образов.
  Один нагрузчик принимает id выбранного сценария в своём контексте.
- `grafanaUrlTemplate` — HTTP(S)-ссылка с `{runId}`, например
  `https://grafana.example/d/postgres?var-run_id={runId}`.
- `loaderImageContext`, `databaseImageContext` — базовые JSON-объекты для образов;
  могут содержать env, argv, конфигурацию и ресурсные лимиты.
- `scenarios` — сценарии с `id`, `title`, `description`,
  списками `settings` и `params`.

Каждое поле схемы: `key`, `title`, `description`, `type`, `defaultValue`, `min`,
`max`, `unit`, `options`. Типы: `INTEGER`, `NUMBER`, `BOOLEAN`, `STRING`, `ENUM`.
Все объявленные поля имеют валидное значение по умолчанию. Пропущенные ключи
заполняются из схемы; явный `null`, неверные типы, значения вне границ и неизвестные
ключи отклоняются. `options` передавайте массивом, включая пустой для обычных полей.
Списки полей могут быть пустыми. Перед сохранением также проверяется совместимость
JSON с PostgreSQL и обратным чтением. Недопустимые символы Unicode и числа вне
поддерживаемого диапазона возвращают 400 до вызова коллектора.

Изменять описание можно через POST/PUT или непосредственно в БД. Обновление каталога
действует сразу, кеша в процессе нет. При прямой SQL-правке необходимо сохранять
корректное определение и существующий `collectorId`; схема и лимиты повторно
проверяются при запуске. PUT заменяет определение целиком. Контексты существующих
задач остаются прежними.

## Коллекторы

`generic` передаёт образам структурированный JSON без специальной конвертации:

- в `databaseImageContext.settings` помещает нормализованные `settings`;
- в `loaderImageContext.params` — нормализованные `params`;
- в `loaderImageContext.scenarioId` — выбранный сценарий;
- остальные базовые ключи сохраняет.

`postgres` использует описания сценариев нового PostgreSQL-плагина. Все пять
сценариев запускаются образом `dbehave/postgres-load:0.1.0`; выбор передаётся через
`SCENARIO`. Настройки БД становятся аргументами `docker-entrypoint.sh postgres -c
key=value`, их единицы и булевы значения форматируются через общий каталог
`PgSettings`: MB, kB, ms, s; `true` → `on`, `false` → `off`, `-1` остаётся без
единицы. Конвертация совпадает с `PostgresPlugin.prepare()` из основного плагина.

Параметры нагрузчика становятся переменными `UPPER_SNAKE_CASE`: `durationSec` →
`DURATION_SEC`, `datasetRows` → `DATASET_ROWS`. Совпадающие после конвертации имена и
параметры, перезаписывающие `SCENARIO` или подключение к БД, отклоняются. Добавляются
`DB_HOST=database`, `DB_PORT=5432`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `PGPASSWORD`.
Начальные имя БД, пользователь и пароль — `dbehave`. Для образа БД воркер должен
использовать сетевой alias `database`. Значения настроек передаются отдельными
аргументами без shell-подстановок. Ключи берутся из сохранённого сценария, поэтому
коллектор не подменяет отредактированную в БД форму статическим описанием.

`mongo` строит контексты для `mongo:8.0` и `dbehave/mongo-load:0.1.0`.
Кеш WiredTiger и сжатие коллекции передаются аргументами `mongod`, подтверждение
журнала и временные файлы отчёта — настройками нагрузчика. Как и для PostgreSQL,
параметры сценария передаются переменными `UPPER_SNAKE_CASE`. Worker монтирует
`/data/db` согласно `WORKER_DB_DATA_STORAGE`, а `/data/configdb` — в tmpfs.
У PostgreSQL и MongoDB отдельные дашборды Grafana. Список запусков на каждом
дашборде фильтруется по метке `engine` метрики `dbehave_run_info`.

Для специальной конвертации реализуйте `ContextCollector` из `plugin-api` и
зарегистрируйте его как Spring-бин. `id()` возвращает значение `collectorId`,
`collect(plugin, scenario, settings, params)` — `ImageContexts` для двух образов.
Коллектор получает уже проверенные поля и должен только строить контекст, без
побочных эффектов. Для недопустимой комбинации параметров можно выбросить
`IllegalArgumentException`: API вернёт 400 с ошибкой поля `context`, задача не
будет записана. Идентификаторы коллекторов должны быть уникальными.

Чтобы подключить плагин, использующий существующий коллектор, достаточно записи
каталога. Для нового способа конвертации понадобится новый бин и сборка бэкенда.
При регистрации и обновлении платформа проверяет сборку каждого сценария на
значениях по умолчанию, чтобы отклонить некорректную конфигурацию коллектора.
PostgreSQL-коллектор проверяет команды обоих образов как массивы строк.
Для `mixed` сумма `readWeight`, `updateWeight`, `insertWeight` должна быть больше
нуля. Для `read-heavy` то же правило действует для `pointWeight`, `rangeWeight`,
`reportWeight`.
Образы выбирает платформа из каталога; коллектор возвращает только их контексты.

## Ресурсы и BDUI

В обоих контекстах можно задать:

- `core_max` — положительное конечное число ядер CPU, например `0.5` или `2`;
- `mem_max` — положительное целое число байт до `9223372036854775807`, например
  `536870912` для 512 MiB.

Значения из запроса заменяют соответствующие значения из определения плагина.
Пропуск сохраняет базовый лимит; если его тоже нет, ключ не записывается и лимит
определяется воркером. Чтобы убрать базовый лимит, обновите определение плагина.
`null` и нулевые значения отклоняются. Фронт не отправляет незаполненные поля.

BDUI содержит секции `settings`, `params`, `loaderImageContext`,
`databaseImageContext`. `fields[].name` — путь в запросе и в `fieldErrors`, например
`databaseImageContext.mem_max`. Для CPU `min=0`, `minExclusive=true`: значение должно
быть больше нуля; для остальных полей границы включительные. Присланные пользователем контексты допускают только два ресурсных
ключа; произвольные env и конфигурация определяются каталогом и коллектором.
Ресурсные значения накладываются платформой после коллектора.

## Очередь

`POST /api/experiments` сначала полностью проверяет и собирает контекст, затем
создаёт запись `worker.tasks` и сведения для истории в `dbehave.experiments`
в одной транзакции. Ответ содержит `id`, `state=QUEUED`,
`grafanaUrl` с подставленным UUID, названия плагина и сценария, времена и текущий
статус. Заголовок `Location` указывает на страницу API данного запуска. Повторный POST создаёт отдельный запуск.
`/validate` использует ту же сборку, возвращая `VALIDATED/READY` без INSERT.

Структура `worker.tasks`:

| Поле | Тип | Назначение |
|---|---|---|
| id | uuid, PK | Идентификатор запуска, совпадает с run id Grafana |
| state | varchar(64) | Начальное `QUEUED`, далее строка, управляемая воркером |
| created_at | timestamptz | Создание задачи |
| updated_at | timestamptz | Автоматически обновляется триггером при любом UPDATE |
| context | jsonb | Снимок исполнения |
| heartbeat | timestamptz, nullable | Последний heartbeat воркера |
| worker_id | varchar(255), nullable | Воркер, взявший задачу |
| error | text, nullable | Ошибка исполнения |

```json
{
  "loaderImageName": "dbehave/postgres-load:0.1.0",
  "databaseImageName": "postgres:18",
  "loaderImageContext": {
    "environment": {"SCENARIO": "mixed", "CLIENTS": "16"},
    "command": [],
    "core_max": 0.5,
    "mem_max": 536870912
  },
  "databaseImageContext": {
    "environment": {"POSTGRES_DB": "dbehave"},
    "command": ["docker-entrypoint.sh", "postgres", "-c", "shared_buffers=128MB"],
    "core_max": 2,
    "mem_max": 1073741824
  }
}
```

Пример показан сокращённо: коллектор добавляет все необходимые env. Воркер читает
образы и их контексты напрямую из задачи; повторно получать плагин ему не нужно.
Платформа не выполняет контейнеры и не меняет статус после `QUEUED`.

Для нескольких воркеров задачу можно атомарно забрать таким запросом:

```sql
WITH next_task AS (
    SELECT id
    FROM worker.tasks
    WHERE state = 'QUEUED'
    ORDER BY created_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE worker.tasks AS task
SET state = 'RUNNING', worker_id = :worker_id, heartbeat = clock_timestamp()
FROM next_task
WHERE task.id = next_task.id
RETURNING task.*;
```

Далее воркер обновляет heartbeat и завершает задачу, например состоянием
`SUCCEEDED` или `FAILED` с `error`. Политика повторных попыток и восстановления
после потерянного heartbeat остаётся на стороне воркера. Polling API каждый раз
читает БД и возвращает статус, времена, heartbeat, workerId, error, названия
плагина и сценария, а также сохранённую ссылку Grafana. Ссылка и названия берутся
из снимка на момент запуска и доступны после перезагрузки страницы.

## Совместимость с master

Для обычного клиента сохранён простой контракт:

| Метод | Адрес | Данные |
|---|---|---|
| GET | `/api/plugins` | Список `{id, title}` |
| GET | `/api/scenarios?pluginId=postgres` | Список `{id, title, description}` |
| GET | `/api/ui/experiment?pluginId=postgres&scenarioId=mixed` | BDUI-секции |
| POST | `/api/experiments` | Создать задачу; то же тело формы, что у `/validate` |
| GET | `/api/experiments` | Последние 100 запусков, новые первыми |
| GET | `/api/experiments/{id}` | Запуск, текущий статус и ссылка Grafana |
| DELETE | `/api/experiments/{id}` | Удалить запуск из истории, ответ `204` |
| DELETE | `/api/experiments` | С телом `{"runIds":["UUID1","UUID2"]}` удалить выбранные, без тела очистить всю историю, ответ `204` |
| POST | `/api/experiments/compare` | Принять `{"runIds":["UUID1","UUID2"]}`, вернуть `{"grafanaUrl":"..."}` |

Административные методы: `GET /api/plugins/{id}` возвращает полное определение,
`POST /api/plugins` регистрирует, `PUT /api/plugins/{id}` заменяет его,
`GET /api/context-collectors` перечисляет доступные бины. Фронтенду не нужно
знать устройство коллектора. Имена PostgreSQL-параметров берутся из текущей формы:
`datasetRows`, `readWeight`, `updateWeight`, `insertWeight`, `warmupSec` и другие.
Старые `rows` и `readPercent` не входят в новую форму.

V3 обновляет нетронутый начальный PostgreSQL-плагин и удаляет устаревшее поле
`loadGeneratorTag` из сохранённых сценариев. Определения с пользовательскими
правками сохраняются. Если вручную задан старый шаблон образа `{scenarioTag}`,
замените `loaderImageName` на реальный общий образ через PUT; запуск до исправления
вернёт 400 с полем `loaderImageName`. Уже записанные задачи не изменяются.

## Интерфейс запуска

Кнопка «Запустить эксперимент» отправляет форму на `POST /api/experiments`.
Ошибки параметров отображаются рядом с полями. После создания задачи открывается
`/experiments/{id}` со статусом и ссылкой Grafana. Активный запуск опрашивается
каждые две секунды. После завершения polling останавливается. При временной ошибке
соединения выполняется повторный GET, данные последнего ответа остаются видимыми.

История `/experiments` получает последние 100 запусков из БД и обновляется, пока
среди них есть активные. Названия плагина и сценария и Grafana URL сохраняются
в `dbehave.experiments`, статусы читаются из `worker.tasks`. Создание обеих записей
атомарно. Старые задачи доступны с пустыми полями описания и ссылки, если эти
сведения ещё не были сохранены.

В `configuration` API возвращает снимок нормализованного запроса запуска.
`settings` и `params` включают применённые значения по умолчанию, а
`loaderImageContext` и `databaseImageContext` содержат ресурсные лимиты
итогового контекста. Изменение каталога сохраняет снимки существующих запусков.
У старых записей `configuration = null`. На странице запуска снимок раскрывается
через «Параметры запуска».

Удаление истории сохраняет задания и их метрики. Идентификаторы удалённых записей
хранятся в `dbehave.hidden_experiments`; история и API запуска исключают их из
выборки. Повторное удаление существующего задания возвращает `204`, неизвестный
UUID — `404`. Очистка охватывает все существующие записи, включая задачи без
`dbehave.experiments` и записи за пределами последних 100. Новые запуски после
очистки доступны в истории.

Фронтенд удаляет записи через выбор галочками и кнопку «Удалить выбранные».
«Выбрать все» отмечает отображаемые записи, до 100 запусков. Перед отправкой
открывается модальное подтверждение с количеством выбранных записей. API принимает
их в `runIds` и проверяет все UUID перед изменением истории. Неизвестный UUID
возвращает `404` и сохраняет весь выбранный набор. Пустой или некорректный список
возвращает `400`.

Для сравнения нужны одинаковый `scenarioId` и точное совпадение сохранённого
`grafanaUrlTemplate`. Разные плагины с одинаковым шаблоном и типом сценария можно
сравнивать. Шаблон для нескольких запусков должен содержать `{runId}` в значении
переменной Grafana, например `?var-run_id={runId}`. API повторяет этот параметр
для каждого UUID, сохраняет остальные параметры URL и удаляет повторы UUID.
Пустой список и несовместимые запуски возвращают `400`; отсутствующий или
удалённый из истории UUID — `404`. Сравнение использует сохранённые сведения
запусков. Для старых записей миграция V5 восстанавливает шаблон из сохранённой
ссылки, если она содержит UUID запуска.

Все `grafanaUrl`, включая ссылки старой истории и сравнения, содержат
`kiosk=1`. Grafana открывает борд с селекторами переменных. Исходный
`grafanaUrlTemplate` сохраняется для проверки совместимости запусков.
